# Set up authenticator-app 2FA in the existing M2 project

The code is prepared locally. The VM database and running server have not been
changed automatically. You apply the update and run the checks below.

Two factors are required for an **enrolled account**: its existing Discard
password and a code generated by an authenticator app. Accounts are not enrolled
automatically. Communication encryption remains M3 work.

## 1. Prepare your phone

Use a TOTP authenticator app you already trust, or install Google Authenticator
from your phone's official app store. This app generates a six-digit code every
30 seconds; it does not receive an email from Discard.

Turn on automatic date and time on your phone. Both the phone and server use
the current time to calculate the code, so an incorrect clock causes rejection.

## 2. Close the clients and stop ChatServer

Close both Discard Windows clients. This allows replacing their executable and
ensures the next sign-in uses the updated login flow.

In the Ubuntu terminal where ChatServer is running, press **Ctrl+C**. This stops
ChatServer while you rebuild it; PostgreSQL and the backup timer remain running.

Create a fresh backup before changing the database:

```bash
sudo systemctl start discard-db-backup.service
```

`sudo` authorizes the system service action. `systemctl start` runs the existing
backup job immediately. It uses the backup script you already installed.

## 3. Update the Windows client and optionally run the local algorithm check

In **Windows PowerShell**, enter the existing source directory:

```powershell
Set-Location 'C:\Users\giler\Desktop\C++\Discard'
```

`Set-Location` changes PowerShell's working directory, so the relative paths
below refer to this project.

The offline checker is optional. Its source, `server/tests/totp_vectors.cpp`,
is retained locally but is not tracked in Git, so a fresh clone does not include
it. Skip the checker instructions if that local file is absent; it is not needed
to build or run Discard or ChatServer.

If you retained the local tests, configure and build the checker with the Qt and
compiler runtime folders on your PATH:

```powershell
$env:PATH = 'C:\Qt\6.9.2\mingw_64\bin;C:\Qt\Tools\mingw1310_64\bin;' + $env:PATH
& 'C:\Qt\Tools\CMake_64\bin\cmake.exe' -S . -B '.\build\vscode-release' -DDISCARD_MFA_CHECKS=ON
& 'C:\Qt\Tools\CMake_64\bin\cmake.exe' --build '.\build\vscode-release' --target DiscardTotpChecks --parallel 2
& '.\build\vscode-release\server\DiscardTotpChecks.exe'
```

The PATH change applies only to this PowerShell session. `&` launches each
program. The first CMake command enables the optional checker in the existing
build; the second builds only `DiscardTotpChecks`, using up to two jobs at once.
Run the executable only after a successful build. It compares the algorithm
against the published RFC 6238 examples, including
leading zeros, malformed input, and code expiry. Expect **TOTP checks passed**.
This checks the algorithm locally; it does not connect to or change the VM.

Replace the client executable in your existing portable client folder:

```powershell
Copy-Item -LiteralPath '.\build\vscode-release\Discard.exe' -Destination 'C:\Users\giler\Desktop\docs\m2-setup-20261009\Discard-M2-Windows\Discard.exe' -Force
```

`Copy-Item` copies the newly built executable. `-LiteralPath` treats the source
as an exact filename. `-Force` replaces the older executable. Keep the existing
Qt DLLs beside it; this change adds no client runtime dependency.

Copy the bundled QR encoder's license beside the executable too:

```powershell
Copy-Item -LiteralPath '.\third_party\qrcodegen\LICENSE' -Destination 'C:\Users\giler\Desktop\docs\m2-setup-20261009\Discard-M2-Windows\LICENSE-qrcodegen.txt' -Force
```

This includes the license notice for the QR encoder compiled into Discard.

## 4. Transfer the server update to the VM

Still in **Windows PowerShell**, upload the prepared archive:

```powershell
scp -P 42222 '.\build\m2-totp-server-update.tar.gz' 'discard@127.0.0.1:/home/discard/m2-totp-server-update.tar.gz'
```

`scp` copies a file over SSH. `-P 42222` selects your existing forwarded SSH port.
The username is the Ubuntu account `discard`; enter its Ubuntu password if
prompted. This archive contains the changed server source, migration, guide,
and checker. It contains no database password or real authenticator secret.

In **Ubuntu**, extract it into the existing project:

```bash
tar -xzf ~/m2-totp-server-update.tar.gz -C ~/Discard
```

`tar` opens the archive. `-x` extracts it, `-z` reads gzip compression, `-f`
selects the archive, and `-C` selects the destination. It replaces the listed
server source files inside the existing `~/Discard` project.

## 5. Add the two MFA tables

In **Ubuntu**, run the migration **once**:

```bash
sudo -u postgres psql -X -v ON_ERROR_STOP=1 -1 -d chatdb -f - < ~/Discard/server/mfa-migration.sql
```

This updates the **real `chatdb`** with the tables needed for 2FA:

- `user_mfa` holds each enrolled account's authenticator seed, last accepted
  time step, and incorrect-code cooldown.
- `mfa_recovery_code` holds hashes of its unused recovery codes.

Existing users, messages, files, and friendships are preserved. The runtime
account receives rights on these two new tables only; message deletion rights
are not expanded.

Command details: `sudo -u postgres` runs as the database administrator;
`psql` is PostgreSQL's terminal client; `-X` ignores personal startup settings;
`ON_ERROR_STOP=1` stops on an error; `-1` applies the whole migration as one
transaction; `-d chatdb` selects the destination; `-f -` reads SQL from stdin.
The final `<` lets your Ubuntu shell read the file from your home directory and
pass it to PostgreSQL, avoiding the home-directory permissions issue encountered
earlier.

Expect two **CREATE TABLE** messages, followed by **REVOKE** and **GRANT**.
If any error appears, stop and share it. Do not rerun an already successful
migration: it is intentionally apply-once.

## 6. Build and start the updated server

In **Ubuntu**, configure the existing server build:

```bash
cd ~/Discard/server
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DDISCARD_MFA_CHECKS=OFF
cmake --build build --target DiscardChatServer --parallel 2
```

`cd` enters the server source directory. `cmake -S .` uses that source;
`-B build` uses the existing build folder; `Release` selects the optimized build;
`DISCARD_MFA_CHECKS=OFF` leaves the optional local checker out of the build.
The second command compiles ChatServer, using up to two jobs at once. This normal
server build does not require any files from `server/tests`. Continue only after
a successful build.

If you also retained or transferred `server/tests/totp_vectors.cpp` locally on
the VM, you can optionally configure, build, and run the checker on Ubuntu too:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DDISCARD_MFA_CHECKS=ON
cmake --build build --target DiscardTotpChecks --parallel 2
./build/DiscardTotpChecks
```

`DISCARD_MFA_CHECKS=ON` requests the checker, and `--target DiscardTotpChecks`
builds that executable specifically. Run it only after a successful build.
Expect **TOTP checks passed**; it does not read or write the database. Skip these
optional commands on a fresh clone, which does not include the local test
source. If the source is absent, CMake skips the checker even when its option is
on; the checker target is therefore unavailable, while ChatServer still builds.

Check the VM clock:

```bash
timedatectl status
```

This displays the system time and synchronization state. The date and time
must be accurate; ideally **System clock synchronized: yes**. If the clock is
wrong, fix that before enrolling accounts. The displayed timezone can differ
from the phone's timezone; TOTP uses the underlying Unix time.

Start ChatServer:

```bash
./build/DiscardChatServer --bind 0.0.0.0
```

The program uses the existing external database configuration and default port
1234. `--bind 0.0.0.0` accepts connections on the VM interfaces used by your
Windows forwarding rule. Expect **Discard ChatServer listening on ... 1234**.
Leave this terminal open: it is running ChatServer.

## 7. Enable 2FA for Alice

Open your existing portable **Discard-M2-Windows\Discard.exe** on Windows and
sign in as Alice. This first sign-in uses her password because she has not yet
enrolled a second factor.

Open **Two-factor Authentication**, then **Set up two-factor authentication**. Enter
Alice's current **Discard password**, not an Ubuntu or PostgreSQL password.
This password confirmation prevents an unattended logged-in client from adding
a factor without knowledge of the account password.

Discard shows a **QR code**, generated locally inside the client. On your phone:

1. Open your authenticator app and choose **Add account**.
2. Choose **Scan a QR code** (wording may vary by app).
3. Scan the QR code displayed by Discard. The app imports the account and setup key.

If scanning is unavailable, choose **Can't scan? Enter key manually** in Discard.
In the phone app choose **Enter a setup key**, enter the displayed key, give the
account a recognizable name such as **Discard - Alice**, and select **Time based / TOTP**.

The QR code contains the same private key as manual setup. Keep both out of
evidence screenshots; the key lets the phone and server calculate matching codes.

Enter the phone's current six-digit code into Discard and click **Enable 2FA**.
This proves the phone has the correct key before the server enables the factor.
The setup expires after five minutes; restart setup if it expires.

## 8. Save the recovery codes

Discard displays ten recovery codes **once**. Save them in a password manager,
write them down somewhere private, or use **Save recovery codes to a file** and
choose a private location. Do not store them in the evidence folder or Git.

Each recovery code can replace the phone code for one sign-in. This gives you
a way to regain access if the phone is unavailable. Tick **I have saved or
written down my recovery codes**, then **Done**. Do not discard the phone entry.

## 9. Demonstrate that the second factor is required

Close Alice's Discard client, then reopen it. This creates a new connection;
an already authenticated connection is not a test of the new login requirement.

Enter Alice's correct username and password. Expect the **Verify your sign-in**
prompt, while the chat window stays closed. This is the essential password-only
test: the server has accepted the password but has not granted account access.

Enter one incorrect six-digit code. Expect rejection. Then wait until the
authenticator displays a **new** code and enter it. Expect normal chat access.
The enrollment code was already consumed, so reusing it immediately will fail.

Capture the code prompt and rejection with secrets/codes hidden, and capture
successful access if needed. Do not show the setup key or recovery codes.

## 10. Test recovery and persistence

Close and reopen Alice's client. After the password, enter one saved recovery
code instead of the phone code. Expect access. Cross that code off your saved
list. **Account security** should now show nine unused recovery codes.

Close and reopen again and try that same recovery code. Expect rejection.
Then sign in with a fresh phone code. This demonstrates single-use recovery.

For a restart check, close the clients, stop ChatServer with Ctrl+C, and start
it with the same command from step 6. Sign in again: Alice should still require
her phone or an unused recovery code. The factor is stored in PostgreSQL, not
only in the running server's memory.

Use the existing Ubuntu backup service again after enrollment so the recovery
data is included in a current backup:

```bash
sudo systemctl start discard-db-backup.service
```

New backups now contain eleven public tables, including MFA seeds and recovery
hashes. They remain sensitive and use the existing restricted VM directory.

## Additional server-side checks

The code prompt alone does not prove that a modified client cannot bypass it.
Using your graphical TCP client, keep a single connection to Windows
`127.0.0.1:41234`, send one compact JSON object per line, and finish each with a
newline. Use only the local M2 environment and a test account.

1. Send `login` with the enrolled account's correct username/password. Expect
   `result.mfa_required: true` and no user profile.
2. Before submitting any code, send `messages` for conversation 52. Expect
   `authentication_required` and no message data.
3. Submit `login_verify` with a fresh phone code. Expect the account profile.
4. Send `messages` again. For Alice, the normal conversation data is allowed.
5. On a new connection, submit `login_verify` before `login`. Expect
   `authentication_expired` and no account access.

Example protected request, containing no password or second-factor secret:

```json
{"type":"messages","request_id":"2","args":{"conversation_id":52}}
```

Each operation's `request_id` must be a nonempty string. `login` arguments are
`username` and `password`; `login_verify` arguments contain only `code`. The
pending identity is held by the server socket; there is no user ID to supply.

Five incorrect factor attempts lock that account's factor verification for
five minutes. Reconnecting does not remove that database-held cooldown. Test
this separately after normal enrollment/login/recovery, then wait the full
cooldown before continuing. Never include actual test passwords or recovery
codes in published request screenshots.

## If setup completed but the recovery-code reply was lost

A disconnected or timed-out confirmation can leave MFA enabled even though the
client did not receive its recovery codes. Keep the authenticator entry you just
added. Reconnect and sign in with a fresh phone code, then open **Account
security**. If MFA is enabled but you never received the recovery-code list,
disable it using your current password and a fresh phone code, then set it up
again and save the new recovery codes. This replaces the inaccessible recovery
list; it does not bypass either factor. The new setup uses a new seed, so replace
the old authenticator entry only after the new setup is confirmed.

## Scope and validation status

Prepared: local source, schema migration, Windows binaries, offline checker,
and server source archive. Compiled locally; user functional tests are pending.
The VM installation is performed by the steps above, not assumed completed.

MFA is opt-in. It protects future password-based logins for enrolled accounts;
it does not evict existing authenticated sessions. Authenticator seeds are
stored in the restricted server database and included in its backups. Recovery
codes are stored as hashes. Passwords still use the existing unsalted SHA-256
format. Password throttling spans connections but resets on server restart;
factor cooldown persists in the database. Neither TOTP nor recovery codes
protect an actively intercepted TCP connection. TLS and server-identity checks
remain M3 work. No production-security or NIST assurance-level claim is made.

Sources: [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238),
[OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html),
[Google Authenticator help](https://support.google.com/accounts/answer/1066447).
